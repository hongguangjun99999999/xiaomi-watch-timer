# 随机提醒（Redmi Watch 6 震动版）

把 [zeenzeen.com/random-reminder](https://zeenzeen.com/random-reminder/) 的「随机提示音」搬到手表上：
90 分钟专注里，每隔 3~5 分钟随机震你一下，提醒抬头休息 5~15 秒。铃声换成震动。

- 直接下载：**[random-cue-v1.1.2.rpk](https://github.com/hongguangjun99999999/xiaomi-watch-timer/releases/download/v1.1.2/random-cue-v1.1.2.rpk)**（31 KB，适配红米手表 6 蓝牙版）

## 它与网页版的关系

算法是从网页版 minified 源码里逐行解出来的，不是"照着描述重写"：

| 项 | 网页版 | 这个应用 |
|---|---|---|
| 专注时长 | 90 分钟 | 90 分钟（可调 5~180） |
| 大休息 | 20 分钟 | 20 分钟（可调 0~60） |
| 提醒间隔 | 2~5 分钟 | 3~5 分钟（可调） |
| 微休息 | 固定 10 秒 | 5~15 秒随机（可调） |
| 随机算法 | 真随机 / 新专注算法 | 两套都移植了 |
| 提示 | 提示音 | 震动节奏 |

「新专注算法」的真实逻辑（原版 `randomMechanism === '新专注算法'` 分支）：

- 前提：专注 ≥ 40 分钟，且间隔区间跨度 ≥ 120 秒，否则退回真随机
- 前 21 分钟（≤1260 秒）：均匀随机
- 最后 15% 时段：均匀随机
- 中间时段：`min + pow(random, 0.1) * (max - min)`
  这个 0.1 次方会把结果压向区间上沿，也就是**中段更容易抽到长间隔**，避免越做越烦。

## 为什么用微服务

快应用页面切到后台或息屏后可能被挂起，页面里的 `setInterval` 不保证继续跑。
90 分钟的计时如果依赖页面，表一黑就废了。

官方「微服务」能让代码脱离应用生命周期在后台运行，且服务端可用接口表里明确包含
`system.vibrator: all`。所以架构是：

```
页面（只负责显示和按钮）
   │  serviceclient.connect({policy:'always'})
   ▼
微服务 focus-timer（计时 + 震动 + 广播状态）
```

页面关掉、应用退到后台，服务仍在跑。页面重新打开时连上来拿一次快照即可。

如果本机不支持微服务（连接抛错或 onerror），页面会自动退回「前台计时」，
并在界面上提示——功能还能用，只是不能息屏。

## 息屏这件事：三层保险

手表息屏后，**第三方快应用没有真正的后台运行权限**。官方规定的后台运行只认
`system.audio` / `system.request` / `system.geolocation` 三种接口在跑，
而且审核要求合理性——一个计时器占这三者任何一个都不合适。

所以不假装能后台常驻，改成三层兜底：

| 层 | 做法 | 覆盖什么 |
|---|---|---|
| 1. 常亮 | 默认开启 `setKeepScreenOn`，运行中每 60 秒重申一次 | 屏不灭，进程不被挂起，提示照常发出 |
| 2. 微服务 | 计时放 `services/focusTimer.js`，`policy:'always'` | 页面被销毁/切换时，计时仍继续 |
| 3. 挂起自愈 | 检测 tick 间隔异常 → 重算相位 + 补发一次提示 | 万一还是被挂起，回来不漏关键提示 |

第 3 层的细节：`loop()` 发现相邻两次 tick 差了 > 4 秒（正常 500ms），就判定被挂起过。
此时**不逐个补震**（一次挂起可能攒好几个事件，连震一串会吓人），只补最有用的一个：
微休息开始优先，其次大休息结束，且只在挂起 10 分钟以内补——太久之前的"该休息"没意义。
界面同时显示「息屏被挂起 X，已重新对齐」，让你知道刚才为什么没收到。

仍然做不到的：**屏幕关着的时候不会震动**。这不是代码问题，是系统不允许。

## 时间戳驱动，不是 tick 累加

`engine.js` 全程用绝对时间戳（`Date.now()`），tick 只做「把状态推进到当前时刻」。
好处是：即使系统把进程挂起几分钟，恢复后也能一次性算出正确的相位，而不是把丢掉的
时间当成 0 秒继续跑。

tick 返回的每个事件都带 `lag`（应该触发的时刻距今多久）。正常运行时只有 `lag ≤ 4 秒` 的才震动；
判定为「刚从挂起中恢复」时，走上面第 3 层的补发逻辑。

暂停恢复是把所有绝对时间戳整体平移暂停时长，所以暂停 30 分钟后，专注结束时间也跟着推后
30 分钟（已用模拟验证：剩余时间差 0ms）。

## 环形进度：全程都是倒计时

三个阶段统一成一种视觉语言 —— **环的长度 = 这一阶段还剩多少**，从满格往回收：

| 阶段 | 环 | 颜色 | 起点 |
|---|---|---|---|
| 未开始 | 满环 | 蓝 | 12 点 |
| 专注 | 100 → 0 | 蓝 | 12 点 |
| 微休息 | 100 → 0 | 绿 | 12 点 |
| 大休息 | 100 → 0 | 橙 | 12 点 |

`start-angle: 0deg` —— 文档写明「以时钟 0 点为基线，正数顺时针」，所以 0 就是 12 点。
`total-angle` 必须为正；取负数会变成逆时针从起点往回画。

早先专注用的是「已过比例」（从 0 涨到满），和两段休息的倒计时方向相反，
同一个界面里两种语义，看着很别扭。现在统一了。

微休息结束时环会从 0 跳回专注的剩余比例（例如 45%），这是"一条弧只能表示一个值"
的必然结果；由于微休息只有十几秒，实际观感是"短计时器用完了，回到大计时器"。

## 震动编码

Watch 6 只支持 `vibrate({mode:'long'|'short'})`，**没有强度参数**，`long` 就是它能给出的最大力度。
所以想让震动"更重"，只有两个手段：用 `long`，以及**把两下之间的间隔压紧**，
让它们连成一片，手腕上感受到的是一段持续压感，而不是几下轻飘飘的点。

一律「两下一组的长震」，靠**几组**区分事件：

| 事件 | 节奏 | 手法 |
|---|---|---|
| **该休息了**（微休息开始） | ●● | 1 组，两下 |
| **继续工作**（微休息结束） | ●● — ●● | 2 组，四下 |
| **专注结束** | ●● — ●● — ●● | 3 组，六下 |
| **大休息结束** | ●● — ●● — ●● — ●● | 4 组，八下 |

组内间隔 170ms（两下连成一段），组间 420ms（能听出手上的"顿"）。

**为什么不是一下**：单次 `long` 只是一个约 0.4 秒的孤脉冲，戴在手上经常被当成
普通通知忽略掉。「继续工作」原来就是一下，实测几乎无感，所以改成两组。

**为什么用"组"而不是单纯数下数**：2/3/4/5 下很容易数错；成对分组以后只数几组，
组间那个 420ms 的停顿是很清楚的分界。

三档强度只动间隔，不动下数（次数已经用来区分事件了）：
轻 = 全部间隔 ×1.7、标准 = ×1、重 = ×0.7 且下限 120ms。
120ms 是下限——挨得比这更近会被系统合并成一次，那是变弱不是变强。

## 构建

已经编译好的安装包就在：

```
dist/com.tang.randomcue.debug.1.1.2.rpk
```

要自己重新编译：

```bash
cd random-cue
npm i
npx aiot build          # 或 npm run build
```

产物在 `dist/*.rpk`。debug 包不需要签名，直接能装。

### 编译期三个必须知道的规则（都是实测撞出来的）

**1. `router.pages` 的 key 决定页面目录**

编译器按 `src/<page key>/<component>.ux` 拼路径。所以目录是 `src/pages/Home/index.ux` 时：

```json
"router": {
  "entry": "pages/Home",
  "pages": {
    "pages/Home": { "component": "index", "path": "/" }
  }
}
```

写成 `"Home": { "component": "index" }` 会去找 `src/Home/index.ux`，然后报「file path does not exist」。
`router.entry` 也要跟着写 `pages/Home`。

**2. 服务的 `path` 要和源文件名完全一致，且打包后会变驼峰**

`path: "services/focus-timer"` 会让打包器输出 `services/focusTimer.js`，
但 manifest 里仍是 `focus-timer` —— 运行时按 path 找不到服务，`connect()` 返回 1001。

正解：源文件直接叫 `focusTimer.js`，`path` 写 `services/focusTimer`，三者对齐。

**3. `system.serviceclient` 不在编译器的 feature 白名单里**

编译会给一条 `unknown feature: system.serviceclient` 的橙字警告，但它**仍然必须写进 `features`**——
不写就报 `missing feature` 直接编译失败。这条警告是编译器的白名单没更新，忽略即可。

同理 `system.router` 也必须显式声明，尽管文档说 router 无需声明。

## 必须先实测的 5 件事

这个工程没在真机上跑过（本机没有 AIoT 工具链）。按顺序验，出问题定位快：

1. **微服务能不能连上**
   装好后打开应用看是否有「后台计时不可用」的橙字。
   没有 = 服务正常；有 = 只能前台计时，需要另想办法（这个提示本身就是降级开关）。

2. **息屏后还会不会震**
   开始计时，然后抬腕熄屏，等 3~5 分钟。
   震了 = 微服务真的在后台跑，整个方案成立。
   不震 = 服务被挂起，确认设置里「屏幕常亮」是开着的（默认开）。

3. **服务端能不能 import 公共模块**
   `services/focus-timer.js` 里 `import engineFactory from '../common/engine'`。
   如果编译或运行报模块找不到，把 `plan.js` / `engine.js` 的代码内联进服务文件。
   官方文档没写服务端能不能引项目内模块，这是盲区。

4. **服务端 setInterval 是否稳定**
   上面第 2 条通过就说明稳定。但注意手表省电策略可能在电量低于某阈值时收紧后台。

5. **震动节奏能不能分辨**
   `long` 和 `short` 的实际时长由系统决定，我们没法指定毫秒。
   如果四套节奏听起来一样，改 `buzz.js` 里的 `modes` 数量和 `gap`。

## 已知限制

- **没有表冠/侧键事件 API**，所以不能用「转动表冠调参数」。
- **不能后台常驻到无限长**。官方的后台运行支持只覆盖 audio/request/geolocation，
  微服务的实际保活时长受系统省电策略约束，长会话可能被回收（好在我们做了状态持久化，
  重开能接着算）。
- **微休息到点不会主动亮屏**。震动会来，但要抬腕才看得到内容。
- 设置页改参数只影响**下一次开始**；正在跑的会话沿用开始时的配置。
